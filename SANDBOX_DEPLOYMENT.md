# Kshitij Coder UPI Sandbox Deployment

This guide prepares the existing Flask application to use the separate Laravel UPI Gateway in
Sandbox mode. It does not change payment behavior, deploy services, or enable Live payments.

## 1. Service layout and credentials

Deploy Flask and the gateway as separate services. Keep each service's secrets in that host's
private environment settings or private `.env` file. Do not put credentials in this repository,
frontend files, build arguments, or browser-visible configuration.

### Flask variables

The Flask variable template is [`.env.example`](.env.example). For local work, copy it to `.env`;
for hosting, set these in the hosting provider's secret/environment settings:

| Variable | Where / purpose |
| --- | --- |
| `SECRET_KEY` | Required: unique, high-entropy random value generated by a trusted secret manager. Never use the template value or app fallback. |
| `DATABASE_URL` | Required: production PostgreSQL SQLAlchemy URL using the installed `psycopg[binary]` driver. Local template defaults to SQLite. |
| `FLASK_DEBUG` | Required: `false`. |
| `SESSION_COOKIE_SECURE` | Required: `true` on HTTPS deployment. |
| `SESSION_SAMESITE` | Usually `Lax` when the web app and API share a site. |
| `CORS_ORIGINS` | Required: comma-separated exact frontend origins including scheme and any non-default port; no wildcard. |
| `PORT` | Hosting-provided listening port (default 5000 if unset). |
| `UPLOAD_FOLDER` | Required: absolute persistent directory outside the public web root, writable by the Flask service account. |
| `MAX_VIDEO_UPLOAD_BYTES`, `MAX_NOTE_UPLOAD_BYTES`, `MAX_SUPPORT_ATTACHMENT_BYTES`, `MAX_PAYMENT_PROOF_BYTES` | Optional size caps; defaults are 500 MiB, 25 MiB, 10 MiB, and 5 MiB. Configure matching proxy limits. |
| `ADMIN_NAME`, `ADMIN_EMAIL`, `ADMIN_PASSWORD` | Only needed when creating/promoting an administrator via CLI. Do not keep the password after account creation. |
| `UPI_GATEWAY_BASE_URL` | HTTPS origin of the deployed gateway (Sandbox credentials must use its Sandbox API). |
| `UPI_GATEWAY_API_KEY`, `UPI_GATEWAY_API_SECRET` | Sandbox merchant credentials from the gateway dashboard (`test_key_...`, `test_sec_...`). |
| `UPI_GATEWAY_WEBHOOK_SECRET` | Sandbox signing secret from the gateway dashboard; must match the configured Sandbox webhook. |
| `UPI_GATEWAY_ENVIRONMENT` | Required: `sandbox`. |
| `UPI_GATEWAY_TIMEOUT_SECONDS` | Bounded HTTP timeout; default 10, allowed 1–30. |
| `UPI_GATEWAY_MAX_WEBHOOK_BYTES` | Webhook body cap; default 65536, minimum 1024. |
| `UPI_GATEWAY_RETURN_URL` | Optional HTTPS return URL. Leave blank unless the hostname is allowlisted in gateway settings. |
| `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET` | Legacy optional integration; leave blank for this UPI Gateway deployment. |
| `OPENAI_API_KEY`, `OPENAI_MODEL` | Optional chat integration; unrelated to payment setup. |

`DATABASE_URL` should use the installed psycopg 3 driver, for example:

```text
postgresql+psycopg://USER:PASSWORD@DB-HOST:5432/DATABASE
```

URL-encode special characters in database usernames/passwords. Use a managed secret store or
protected environment variables in hosted production; do not paste secret values into tickets or
logs. Add the PostgreSQL provider's TLS options/CA certificate as required; do not disable
certificate validation to make a connection succeed.

`SECRET_KEY=replace-with-a-long-random-secret` and the admin password in `.env.example` are
instructional placeholders, not usable deployment values. The application has a known development
fallback secret if `SECRET_KEY` is absent, and secure cookies default off for local development.
Set a unique random secret and `SESSION_COOKIE_SECURE=true` in the Flask host settings before
deployment; never deploy using the template unchanged.

## 2. Database and migration safety

The Flask migration chain has one head, `20261125_upi_gateway`:

```text
20261125_initial
  -> 20261125_chat
  -> 20261125_admin_support
  -> 20261125_upi_gateway
```

The local database was observed at this head during the previous local audit. No deployment
database is available here. Before an eventual upgrade, take a verified PostgreSQL backup and
restore it to a separate, isolated clone first. Do not point inspection commands at production
during this preparation.

```bash
pg_dump --format=custom --file=kshitij-before-upgrade.dump --host="$PGHOST" --port="$PGPORT" --username="$PGUSER" --dbname="$PGDATABASE"
pg_restore --list kshitij-before-upgrade.dump > kshitij-backup-contents.txt
```

Supply the password through a protected `.pgpass`/password file or an interactive secure prompt;
do not put it in command arguments or shell history. Protect the backup because it contains
student and payment data. A readable archive listing is only a format check. To verify a dump,
point these commands at an isolated PostgreSQL instance and a new, empty database only:

```bash
createdb --host="$PGHOST" --port="$PGPORT" --username="$PGUSER" "$VERIFY_DB"
pg_restore --exit-on-error --no-owner --host="$PGHOST" --port="$PGPORT" \
  --username="$PGUSER" --dbname="$VERIFY_DB" kshitij-before-upgrade.dump
psql --host="$PGHOST" --port="$PGPORT" --username="$PGUSER" --dbname="$VERIFY_DB" \
  --command='SELECT (SELECT count(*) FROM users) AS users, (SELECT count(*) FROM courses) AS courses, (SELECT count(*) FROM payments) AS payments, (SELECT count(*) FROM enrollments) AS enrollments;'
```

Compare those counts with the source clone before the dump. Never run these restore commands against
the production database or restore over an existing database as a test.

Install dependencies in the build environment. For schema comparison, point
`DATABASE_URL` only at a restored, isolated target clone—not production. In Bash, set the clone
URL from your host's protected environment store:

```bash
export DATABASE_URL="$TARGET_CLONE_DATABASE_URL"
```

These are read-only inspection commands. No database migrations or production database connections were performed for this preparation.

Then inspect repository head and clone revision:

```bash
python -m pip install -r requirements.txt
python -m flask --app backend.app db heads
python -m flask --app backend.app db current
python -m flask --app backend.app db history
```

`db heads` reports the repository head; `db current` reads the selected clone's Alembic revision.
Repeat `db current` against a separate source/staging clone if needed. If the target lacks an
`alembic_version` row, has pre-existing tables without migration history, or differs from the
expected chain, stop and reconcile a restored copy first. Never stamp an unknown schema.

**Only after a separately approved deployment window and a verified restorable backup**, apply
pending migrations to a disposable clone first, then plan the production upgrade:

```bash
python -m flask --app backend.app db upgrade
python -m flask --app backend.app db current
```

The upgrade adds payment gateway fields, event/audit tables and indexes, as well as applying any
earlier missing platform migrations. It does not drop student, course, enrollment, or payment data.
Do not run `db downgrade` for deployment. Test the upgrade against a restored copy of the target
database before applying to a production database.

If a target database has application tables but no Alembic revision, or its schema/history differs
from this migration chain, stop after the backup and inspect a restored copy. Do not run `db upgrade`
or `stamp` blindly; reconcile the schema and revision first. The target deployment database was not
available during this audit.

For the separate Laravel database, use the browser installer as documented by the gateway. It
creates its own tables in its own MySQL database; do not point it at the Flask database.

## 3. Deploy the Laravel gateway separately

The gateway's current repository requires PHP 8.2+, Laravel 12, MySQL 8 or supported MariaDB,
PDO MySQL, and the listed PHP extensions (including cURL, OpenSSL, Mbstring, Tokenizer, XML, JSON,
and Fileinfo). For shared hosting, use its production package with dependencies and compiled assets;
for VPS/source deployments, follow that repository's install guide.

1. Create a dedicated MySQL database and user for the gateway. Grant only the privileges it needs.
2. Deploy the gateway outside the public web root where possible. Point the site's document root at
   the gateway's `public/` directory only.
3. Enable HTTPS and run its browser installer over HTTPS. Configure the database and create a unique
   gateway administrator. Keep installer protection enabled after setup.
4. Set production-safe Laravel configuration as described above. Use database-backed queue/cache
   where appropriate and set `QUEUE_CONNECTION=database`.
5. Start a persistent queue worker from the gateway application directory:

   ```bash
   php artisan queue:work --sleep=3 --tries=3 --timeout=90
   ```

   Configure the host's process manager (for example Supervisor/systemd) to restart it after a
   failure or deployment. Follow gateway-specific hosting notes if they specify different flags.
6. Run Laravel's scheduler every minute using the hosting cron service:

   ```cron
   * * * * * cd /path/to/upi-gateway && php artisan schedule:run >> /dev/null 2>&1
   ```

   The scheduler delivers queued webhook outbox events and runs gateway verification tasks. Confirm
   the configured queue worker and scheduler are actually running in the hosting environment.
7. In the gateway dashboard, create a Sandbox merchant API key/secret pair, configure a Sandbox
   payment account/provider for testing, and copy the Sandbox webhook signing secret securely.
   Keep Sandbox and Live credentials separate.
8. Add the Flask site's HTTPS hostname to the gateway merchant's allowed redirect domains if using
   `UPI_GATEWAY_RETURN_URL`.
9. In the gateway's API & Webhooks settings, set its Sandbox webhook destination to:

   ```text
   https://<FLASK-HOST>/api/payments/upi/webhook
   ```

   Enable the needed events and set the webhook signing secret on Flask to the matching Sandbox
   secret. Do not use a public demo URL as the payment backend.

The gateway connectivity check uses the documented `GET /api/v1/accounts` endpoint with
`X-Api-Key` and `X-Api-Secret`. Run this from the Flask host after the private environment values
are configured. It refuses non-HTTPS URLs, non-Sandbox key prefixes, and redirects; it reads and
validates the response in memory and never prints credentials or response data:

```bash
python - <<'PY'
import json
import os
import sys
from urllib.error import HTTPError, URLError
from urllib.parse import urlsplit
from urllib.request import HTTPRedirectHandler, Request, build_opener

class NoRedirect(HTTPRedirectHandler):
    def redirect_request(self, request, response, code, message, headers, new_url):
        return None

base = os.environ.get("UPI_GATEWAY_BASE_URL", "").rstrip("/")
key = os.environ.get("UPI_GATEWAY_API_KEY", "")
secret = os.environ.get("UPI_GATEWAY_API_SECRET", "")
try:
    parsed = urlsplit(base)
    valid_url = (parsed.scheme == "https" and parsed.hostname and
                 not parsed.username and not parsed.password and
                 not parsed.query and not parsed.fragment)
except ValueError:
    valid_url = False
if not valid_url or not key.startswith("test_key_") or not secret.startswith("test_sec_"):
    print("Sandbox connectivity check: configuration rejected (no request sent).")
    sys.exit(2)

req = Request(base + "/api/v1/accounts", headers={
    "X-Api-Key": key,
    "X-Api-Secret": secret,
    "Accept": "application/json",
})
try:
    with build_opener(NoRedirect).open(req, timeout=10) as response:
        status = response.status
        body = response.read(65537)
except HTTPError as error:
    status = error.code
    error.close()
    print(f"Sandbox connectivity check: HTTP {status}; response omitted.")
    sys.exit(1)
except (URLError, TimeoutError, OSError):
    print("Sandbox connectivity check: connection/TLS failure; details omitted.")
    sys.exit(1)

try:
    payload = json.loads(body.decode("utf-8")) if len(body) <= 65536 else None
except (UnicodeDecodeError, json.JSONDecodeError):
    payload = None
if (status == 200 and isinstance(payload, dict) and payload.get("success") is True
        and payload.get("environment") == "sandbox" and isinstance(payload.get("data"), list)):
    print("Sandbox connectivity check: PASS (HTTP 200; response omitted).")
    sys.exit(0)
print(f"Sandbox connectivity check: unexpected response (HTTP {status}; body omitted).")
sys.exit(1)
PY
```

The Sandbox accounts endpoint intentionally returns an empty list, so this check verifies TLS,
network reachability, API credentials, and the environment without creating an order. To verify the
documented `GET /api/v1/orders/{id}` path, use the Flask status-check flow after an operator creates
a Sandbox order through the student checkout; do not put a response body or credentials in logs.

The current gateway order API accepts amounts from 1.00 through 100000.00 INR. The Flask course
route permits any positive database price, so set Sandbox course prices inside the gateway's range;
out-of-range course prices will be rejected by the gateway. This audit did not change course-price
or payment behavior.

## 4. Deploy Flask

1. Use the deployment's supported Python runtime. `requirements.txt` pins Flask and payment
   dependencies; the current workspace Python 3.10 can install them, but use a maintained Python
   version supported by your hosting provider for the actual deployment.
2. Set Flask environment variables in the host's private environment/secrets panel. Set the UPI
   environment to `sandbox`, Sandbox API key/secret pair, matching Sandbox webhook secret, gateway
   HTTPS base URL, production PostgreSQL URL, a strong `SECRET_KEY`, `FLASK_DEBUG=false`,
   `SESSION_COOKIE_SECURE=true`, and exact `CORS_ORIGINS`.
3. Preserve the instance upload directory on persistent storage. Set reverse proxy upload/body
   limits to match the Flask upload limits. Use HTTPS for the frontend, API, and gateway.
4. Install dependencies, back up the database, run the migration commands above, then launch the
   existing Flask app behind the host's HTTPS reverse proxy. The repository documents this
   Gunicorn entry point for Socket.IO deployments:

   ```bash
   gunicorn --worker-class geventwebsocket.gunicorn.workers.GeventWebSocketWorker \
     --workers 1 --bind 0.0.0.0:${PORT:-5000} backend.app:app
   ```

   Configure `CORS_ORIGINS` to exact browser origins (scheme and hostname, with a port if used).
   Credentialed CORS must never use `*`. Keep Flask's secure, HttpOnly session cookie settings.
   Flask-Limiter currently uses in-memory storage and emits a production warning; the documented
   single-worker setup keeps each process's counters local, but counters reset on restart and are
   not shared across instances. Do not scale Flask across workers/instances expecting shared rate
   limits until a shared limiter store is configured in the application. The current code does not
   read a `RATELIMIT_STORAGE_URI` variable, so setting it in the host alone has no effect. Before
   scaling, add shared-store config before `limiter.init_app(app)`, for example:

   ```python
   app.config["RATELIMIT_STORAGE_URI"] = os.environ["RATELIMIT_STORAGE_URI"]
   ```

   Then set `RATELIMIT_STORAGE_URI=rediss://<PRIVATE-REDIS-HOST>:<PORT>/<DB>` in the Flask
   secret store and install the pinned Flask-Limiter Redis extra (replace the existing requirement
   with `Flask-Limiter[redis]==3.12`). Use private networking, TLS, and a dedicated Redis ACL/user;
   never use an unauthenticated public Redis endpoint. Verify the limiter CLI reports Redis
   storage before scaling. This code/dependency change is a separate prerequisite and was not made
   in this deployment-preparation task.
5. Verify that the deployed API routes exist:

   ```text
   POST /api/payments/upi/orders
   GET  /api/payments/upi/<payment_id>
   POST /api/payments/upi/<payment_id>/check
   POST /api/payments/upi/webhook
   ```

   Student routes require the existing authenticated session. Verify them using a dedicated
   Sandbox student account in a browser, not by weakening authentication. The webhook must accept
   only the gateway's signed raw-body requests.

## 5. Sandbox acceptance checklist

Use a dedicated test student and a published course with a nonzero price set in the database/admin.
Do not use real banking credentials or Live merchant keys.

- [ ] Student can sign in over HTTPS and the session persists with secure cookies.
- [ ] Student opens the paid course and chooses Buy with UPI.
- [ ] Flask takes the amount from the published course record; altering browser `course_id` or
      sending an `amount` field cannot change the server-side course price.
- [ ] Flask creates one internal payment record and one/reused Sandbox order with the gateway.
- [ ] Checkout link opens the gateway's hosted Sandbox checkout; returning to the site alone does
      not grant course access.
- [ ] Complete the gateway's documented Sandbox payment simulation and confirm its order status
      through the authenticated status endpoint.
- [ ] Gateway posts a webhook to the exact Flask webhook URL; inspect Flask audit/event records for
      valid timestamped HMAC verification, matching event identity, order, amount, currency, and
      Sandbox environment.
- [ ] Repeat the same webhook delivery; it is acknowledged as duplicate and does not create a
      second enrollment or reapply state.
- [ ] Student status page and the authenticated status-check endpoint show the verified Sandbox
      result, independent of return URL parameters.
- [ ] Exercise Sandbox failed, expired, pending, and review scenarios using the gateway's supported
      simulation tools. Confirm review maps to the site's `under_review` state and none of these
      states grants course access.
- [ ] Send an invalid signature and a timestamp older than five minutes; both are rejected.
- [ ] Send an older sequence after a newer event; it does not revert the payment state.
- [ ] Another student's session cannot view or check the payment.

Expected status results when exercising each gateway event:

| Sandbox case | Expected Flask result |
| --- | --- |
| `order.paid` with matching order data and successful authenticated status lookup | Payment becomes `captured`; Sandbox enrollment remains absent. |
| `order.failed` | Payment becomes `failed`; no enrollment. |
| `order.expired` | Payment becomes `expired`; no enrollment. |
| `order.pending` or `order.timeout` | Payment remains/maps to `pending`; no enrollment. |
| `order.under_review` with gateway status `review` | Payment becomes `under_review`; no enrollment. |
| Re-delivery of a previously processed `event_id` | HTTP success with `duplicate: true`; no repeated transition. |
| Invalid signature or timestamp outside ±300 seconds | Rejected with HTTP 401; state unchanged. |
| Valid event with lower/equal `event_sequence` than stored | Recorded as stale; newer payment state remains unchanged. |
| Paid event whose authenticated gateway status is not `paid` | Retryable HTTP 503; no enrollment. |
| Amount, currency, order, client reference, or environment mismatch | Rejected; state and enrollment unchanged. |

**Sandbox enrollment limitation:** this Flask app intentionally never activates enrollment for
Sandbox payments, even when the gateway confirms a Sandbox order as paid. Therefore Sandbox testing
can verify order creation, checkout, signatures, status synchronization, and that Sandbox does not
unlock real course access. It cannot verify the Live enrollment-after-payment path. Do not change
this safety behavior merely to make a Sandbox checklist pass; use a separately designed, isolated
test-only flow if that requirement is needed. Live enrollment must remain untested until the Sandbox
acceptance checks pass and a separate, deliberate Live launch is authorized.

## 6. Security review and remaining checks

Static inspection found no gateway API key, API secret, or webhook secret in frontend JavaScript.
The UPI checkout JavaScript only displays the server-provided URL/intent and asks Flask to retrieve
status. The Flask UPI order route derives price from the database; paid status from an event is
rechecked through the authenticated gateway API; webhook event IDs have a unique constraint; event
sequence guards stale state; and enrollment is protected by the `(user_id, course_id)` unique
constraint plus existing-enrollment checks. Admin manual approval is restricted to records whose
provider is `manual`; it cannot approve `upi_gateway` records.

The repo also has legacy Razorpay routes, but the current frontend does not call them and the
Razorpay secrets should remain blank for this deployment. Do not configure Razorpay as a fallback
for this Sandbox integration.

Uploads use size limits, allow-listed filename extensions, sanitized original names, and random
stored names. Uploads are stored outside the frontend's static directory and private proof/support
downloads check ownership or admin permissions. The code checks extensions rather than inspecting
file contents or scanning for malware; keep uploads on non-public persistent storage and apply the
hosting provider's request-size limits.

Before accepting any Live payments, complete the whole checklist against the deployed Sandbox
services, review gateway provider configuration and hosting logs, and perform any required business
and provider account checks. The gateway repository identifies its Paytm for Business verifier as
unofficial/experimental; do not use that provider for production. This guide does not establish that
the target hosting is configured, that a real UPI payment works, or that Live mode is safe to enable.

## 7. Troubleshooting

| Symptom | Checks |
| --- | --- |
| Connectivity script rejects config without sending | Confirm `UPI_GATEWAY_ENVIRONMENT=sandbox`, the gateway base URL is HTTPS with no credentials/query/fragment, and the key pair uses the Sandbox prefixes. |
| Connectivity reports TLS/connection failure | Check DNS, outbound HTTPS from Flask host, gateway certificate validity, firewall rules, and the exact base URL. Do not disable TLS verification. |
| Gateway API returns HTTP 401/403 | Confirm the Sandbox API key and secret belong to the same active merchant and environment. Never paste them into logs or support tickets. |
| API returns 404 | Check base URL/subdirectory prefix and that the gateway API routes are deployed. Do not guess endpoints. |
| Order creation returns validation error | Check course price is 1.00–100000.00 INR and any configured redirect hostname is allowlisted. |
| API returns 429 | Respect the gateway's retry headers and limits; do not run loops or repeatedly retry order creation. |
| Webhook HTTP 401 | Check the gateway and Flask use the same environment's webhook secret, host clocks are synchronized, and the gateway sends the documented raw-body signature headers. Do not log the signature. |
| Webhook HTTP 400/404 | Compare the event's order/client IDs, amount, currency, environment, event type/status, and event sequence with the stored payment and gateway order. |
| Paid webhook receives HTTP 503 | Flask could not confirm the order against the gateway API. Keep the event retryable; restore API connectivity and let the gateway queue retry. Do not manually mark paid. |
| Webhooks are delayed | Check the gateway's queue worker, scheduler cron, durable outbox/delivery logs, and outbound HTTPS to Flask. |
| Browser reports CORS/session errors | Set the exact browser origin in `CORS_ORIGINS`, use HTTPS for both services, and verify Secure/HttpOnly cookie and SameSite behavior. |
| Upload returns 413 or disappears after release | Align reverse-proxy limits with Flask limits and point `UPLOAD_FOLDER` at absolute persistent storage. |
| Flask rate-limit warning | Single-process in-memory limits are active. Complete the shared Redis configuration/code prerequisite before scaling. |
| Alembic target has no revision or unexpected tables | Stop; inspect a restored clone and reconcile migration history. Do not stamp blindly or downgrade. |

Never put credentials, webhook signatures, raw payloads containing personal data, or full API
response bodies in troubleshooting logs. Use event IDs and internal payment IDs where possible.

## 8. Rollback precautions

- Never use Flask or Laravel migration downgrade commands as a deployment rollback. A downgrade can
  remove tables/columns and destroy payment, student, course, enrollment, or gateway event history.
- Before a schema upgrade, retain a verified, access-restricted backup and a tested restore into a
  separate empty database. Record its checksum and retention location under the site's backup
  policy.
- Prefer rolling the application code back while leaving an additive, forward-compatible schema in
  place, but verify compatibility of the exact old release against the new schema first.
- If data restoration is needed, restore into a new database or isolated recovery environment,
  validate student/course/payment/enrollment counts and payment history, and plan an explicit
  reviewed cutover. Never restore a backup over the active database as an untested first action.
- Keep the gateway queue/outbox and payment records intact during an application rollback; queued
  webhooks may be retried and must remain safely deduplicated.
- Keep Sandbox credentials and webhook secrets separate from any later Live setup. Do not switch
  credentials or environment to Live as part of a rollback or troubleshooting step.
